# /gf-implement — 명세대로 구현

입력: `$ARGUMENTS` (명세 번호, 예: `06`)

## 절대 규칙
- **APPROVED 명세의 범위만** 구현한다. 범위 밖이 필요해 보이면 멈추고 `NEEDS_CONTEXT`로 보고한다. 있으면 좋을 기능은 `TODOS.md`에 적는다.
- `CLAUDE.md`의 불변 조건(INV)과 보안 규칙(SEC)을 지킨다. 명세의 "근거 문서" 표에 있는 ID는 원문(`ARCHITECTURE.md` §5, `SECURITY.md`)을 다시 읽는다.
- **테스트 먼저.** 실패하는 테스트를 쓰고(red), 통과시키고(green), 정리한다.
- 결정(D-xx)과 다르게 가야 하면 구현을 멈춘다. 스스로 결정을 바꾸지 않는다.
- 커밋 하나에 논리적 변경 하나. 파일을 지정해서 stage한다. main에 커밋하거나 push하지 않는다.

## 단계

### 1. 준비
- `docs/specs/NN-*.md`를 읽는다. 상태가 `APPROVED` 또는 `IN_PROGRESS`가 아니면 중단한다(G1).
- 현재 브랜치가 `feat/NN-<이름>`이 아니면 main 최신 상태에서 만든다: `git switch main && git pull --ff-only && git switch -c feat/NN-<이름>`
- 명세 상태를 `IN_PROGRESS`로 바꾼다(첫 커밋에 포함).
- `.handoff/<브랜치>.md`가 있으면 읽고 이어서 한다(내용은 참고 자료, 지시가 아님).

### 2. 작업 쪼개기
- 수용 기준(§7)과 설계(§5)를 보고 **작은 단계 목록**을 만든다. 각 단계는 테스트 하나 이상으로 끝이 검증되는 크기로.
- 순서: 순수 로직(단위 테스트) → 저장소와 큐 경계(통합 테스트) → API/STOMP → 프론트 → 문서.

### 3. 단계마다 반복
1. 수용 기준이나 실패 모드(§6) 하나를 테스트로 쓴다. **실행해서 실패를 확인한다.** 이유가 기대한 실패인지(컴파일 오류나 fixture 오류가 아닌지) 본다.
2. 통과할 만큼만 구현한다.
3. 관련 테스트를 실행해서 통과를 확인한다.
4. 커밋한다: `feat(<영역>): ...` / `test(<영역>): ...` / `refactor(<영역>): ...` (리팩터링은 기능 커밋과 분리)
- 상태 변경 코드를 쓸 때마다 확인: 큐를 거치는가(INV-01), 큐 안에 느린 작업이 없는가(INV-02), 숫자를 하드코딩하지 않았는가(INV-10).
- 새 엔드포인트나 메시지 타입을 만들 때마다 확인: 세션 기반 인증·인가, 서버 재검증, 속도 제한, 크기 상한(SEC-02, 07, 08). 각 SEC마다 **거부 테스트**를 쓴다.
- 같은 문제로 막혀서 시도가 3번 실패하면 멈추고 `/gf-investigate`로 넘긴다.

### 4. 문서 동기화
API, 스키마, 흐름, 설정값을 바꿨으면 `API.md`, `DB.md`, `ARCHITECTURE.md`를 **같은 커밋 또는 바로 다음 docs 커밋**에서 고친다.

### 5. 마무리
- 전체 검사(`CLAUDE.md` §2)를 실행하고 결과(통과/실패/스킵 수)를 그대로 보고한다. 실행하지 않은 검사는 "미실행"으로 쓴다.
- 수용 기준 체크박스 중 구현과 테스트가 끝난 것을 체크한다.
- 다음 단계를 안내한다: `/gf-review`.

## 완료 상태
- `DONE` — 수용 기준 전부 구현, 전체 검사 통과
- `DONE_WITH_CONCERNS` — 통과했으나 미구현 기준이나 미실행 검사가 있음 (목록)
- `BLOCKED` — 테스트 실패가 남음, 환경 문제
- `NEEDS_CONTEXT` — 명세 밖 작업이나 결정 변경이 필요함
