# /gf-qa — 시나리오 검증과 수정 루프

입력: `$ARGUMENTS` (명세 번호, 선택적으로 `report-only`)

## 절대 규칙
- **수정 전에 회귀 테스트부터**: 실패하는 테스트로 버그를 재현하고(red), 수정 후 통과를 확인한다(green).
- **최소 수정**: 버그와 관련 없는 리팩터링이나 기능 추가 금지.
- **검증된 수정만 커밋**하고, 수정 하나당 커밋 하나(회귀 테스트 포함).
- 기존 테스트를 약화하거나 지우지 않는다. CI 설정을 바꾸지 않는다.
- `report-only`면 코드를 전혀 바꾸지 않고 보고서만 쓴다.

## 단계

### 1. 준비
- 명세 `docs/specs/NN-*.md`의 수용 기준(§7)과 테스트 계획(§8)을 읽는다.
- 실행 환경을 확인한다: `docker compose up -d mysql`, 백엔드와 프론트 실행 명령은 `CLAUDE.md` §2를 따른다. 환경이 안 뜨면 수정하지 말고 `BLOCKED`로 보고한다(환경 문제를 코드 문제로 착각하지 않기).

### 2. 기준선 실행
- 전체 테스트를 실행하고 결과를 기록한다(통과/실패/스킵 수).
- 수용 기준을 하나씩 확인한다. 각 기준을 **어떤 방법으로 확인했는지** 적는다: 자동 테스트 이름, 실행한 요청과 응답, 브라우저에서 본 것.

### 3. 이 프로젝트에서 반드시 확인할 시나리오
해당 기능에 관련된 것만 실행한다. 다중 클라이언트 시나리오는 Spring의 `WebSocketStompClient` 통합 테스트로 자동화하는 것을 우선한다.

| 영역 | 시나리오 |
|---|---|
| 로딩 (INV-09) | A가 청크를 구독하는 도중 B가 게시 → A 화면에 빠짐 없이, 중복 없이 나타남 |
| 동시 게시 (INV-01) | 70% 직전에 두 사용자가 동시에 게시 → 카운트다운이 정확히 한 번 시작 |
| 쿨다운 (INV-08) | 같은 사용자가 ✓를 연속 두 번(더블클릭) → 하나만 게시, 나머지 429 |
| 페이지 넘김 (D-16) | 모더레이션 중에 페이지 종료 → 409 PAGE_ENDED, 쿨다운 되돌림, 클라이언트 초안 폐기 |
| 권한 (SEC-07) | 남의 doodle 삭제, 비로그인 STOMP SEND, 종료된 페이지 구독 → 전부 거절 |
| 차단 (SEC-15) | 차단 직후 기존 세션으로 게시와 커서 전송 → 거절, 연결 종료 |
| 재시작 (D-25) | 게시 후 서버 재시작 → 점유율과 종료 예정 시각이 같음 |
| ML 그림자 모드 (INV-13) | ML 서버를 멈추거나 응답을 3초 넘게 지연 → 게시는 정상 처리, `ml_prediction.outcome`이 TIMEOUT/ERROR로 기록 / ML이 FLAGGED를 내도 SHADOW에서는 게시됨 |
| ML 판정 (D-35) | 팀 평가 세트의 부적절 낙서와 손글씨 욕설 샘플 → `ml_prediction`에 점수와 OCR 글자가 기록됨 |
| 화면 | 줌 0.5배와 4배 경계, 모바일 두 손가락 이동, T−5분 배너, 미니맵 사각형 위치 |

브라우저 확인은 개발 서버를 띄운 뒤 Claude의 내장 브라우저나 Playwright로 한다. 확인할 수 없으면 "미검증"으로 표시하고 사람이 확인할 항목으로 넘긴다.

### 4. 분류
발견한 문제에 번호를 붙인다: `ISSUE-001`부터. 심각도는 Critical / High / Medium / Low. 환경 문제와 제품 결함, 잘못된 테스트 기대값을 구분한다.

### 5. 수정 루프 (`report-only`가 아닐 때, 심각도 순)
1. **재현**: 최소 재현 절차를 기록한다.
2. **회귀 테스트 작성**: 근처 테스트 2~3개의 이름, 구조, 단언 방식을 따라 새 테스트를 추가한다. 맨 위에 주석을 단다:
   ```java
   // Regression: ISSUE-NNN — 짧은 설명
   // Found by /gf-qa on YYYY-MM-DD, spec NN
   ```
   실행해서 **이 결함 때문에 실패하는지** 확인한다(fixture나 import 오류로 실패한 게 아닌지).
3. **최소 수정** 후 회귀 테스트, 원래 재현 절차, 인접한 정상 경로를 다시 실행한다.
4. **커밋**: 검증된 수정과 회귀 테스트 파일만 지정해서 stage한다. `git add -A`는 쓰지 않는다.
   `fix(qa): ISSUE-NNN — 짧은 설명`
5. **분류**: verified(검증됨) / best-effort(일부만 검증) / reverted(되돌림, 이슈는 남김)
6. **자기 점검**: 수정 5개마다, 그리고 되돌림이 생길 때마다 멈추고 확인한다. **되돌림 2회, 또는 관련 없는 파일을 건드리게 되면 즉시 중단**하고 사용자에게 보고한다. 같은 버그에 가설 3개가 실패하면 `/gf-investigate`로 넘긴다.

### 6. 마무리
- 전체 테스트를 다시 실행하고 결과를 첨부한다.
- 명세의 `## QA 기록`에 추가한다:
  `YYYY-MM-DD · <HEAD SHA 7자리> · 수용 기준 n/n · 시나리오 통과 n 실패 n 미검증 n · ISSUE: 001(verified), 002(TODOS) · 상태`
- 고치지 않은 이슈는 `TODOS.md`나 다음 명세로 넘긴다.

## 완료 상태
- `DONE` — 수용 기준 전부 통과, 미해결 Critical/High 0
- `DONE_WITH_CONCERNS` — 통과했으나 미검증 항목이나 Medium 이하 미해결이 있음
- `BLOCKED` — 환경 문제, 또는 미해결 Critical/High
- `NEEDS_CONTEXT` — 명세의 기대 동작이 모호함
