# /gf-investigate — 근본 원인 먼저

입력: `$ARGUMENTS` (증상, 에러 메시지, 재현 방법)

## Iron Law
**근본 원인을 찾기 전에는 수정하지 않는다.** 증상만 고치면 다음 버그를 더 찾기 어렵게 만든다.

## 단계

### 1. 근본 원인 조사
- 증상을 정확히 기록한다: 무엇을 했을 때, 무엇을 기대했고, 실제로 무엇이 일어났는지. 에러 메시지와 스택 트레이스 원문.
- **재현한다.** 재현할 수 없으면 추측으로 고치지 않는다. 로그를 추가해서 다음 발생을 기다리는 것도 선택지다.
- 최근 변경을 확인한다: `git log --oneline -15 -- <관련 경로>`, `git log --grep=revert --oneline`
- 데이터 흐름을 진입점부터 추적한다. 이 프로젝트에서 흔한 원인 위치:
  - 큐 안/밖 경계 (INV-01, INV-02): 상태가 큐 밖에서 바뀌거나 큐 안에서 느린 작업이 줄을 막음
  - 로딩 순서 (INV-09): 구독과 조회 사이 이벤트 누락이나 중복
  - 페이지 넘김 경계 (INV-04): 옛 pageId 요청, 옛 페이지 이벤트
  - 시간: `Clock`을 주입하지 않은 `now()` 호출, UTC와 로컬 시간 혼용
  - STOMP 인터셉터: 인증 정보가 세션에서 메시지로 전달되지 않음

### 2. 범위 고정
- 가설을 세우면 **수정을 허용할 디렉토리를 선언**한다(예: `backend/.../page/`). 그 밖의 파일은 수정하지 않는다.
- 밖을 수정해야 한다는 결론이 나오면 멈추고 사용자에게 알린다.

### 3. 패턴 분석
- 같은 패턴이 다른 곳에도 있는지 찾는다(다른 컨트롤러, 핸들러, 스케줄러).
- 프레임워크 동작이 의심되면 Spring/STOMP/Konva **공식 문서**에서 확인한다. 추측으로 프레임워크를 탓하지 않는다.

### 4. 가설 검증
- 수정하기 전에 임시 로그나 단언(assert)으로 **증거를 확인**한다.
- 가설이 틀리면 다음 가설로. 외부 검색을 할 때는 호스트명, 이메일, 토큰, 내부 경로를 지운다.
- **3-strike 규칙**: 가설 3개가 실패하면 멈추고 묻는다.
  ```
  가설 3개를 검증했지만 맞는 것이 없습니다. 구조적인 문제일 수 있습니다.
  A) 계속 조사 — 새 가설: ...
  B) 사람에게 넘김 — 시스템을 아는 팀원 확인 필요
  C) 로깅 추가 후 대기 — 다음 발생 때 잡기
  추천: ...
  ```

### 5. 수정
- 근본 원인을 고치는 **가장 작은 변경**. 주변 리팩터링 금지.
- **회귀 테스트**: 수정 전에는 실패하고 수정 후에는 통과해야 한다. 둘 다 실제로 실행해서 확인한다.
- 수정이 **5개 파일을 넘으면** 멈추고 확인받는다: A) 진행 B) 핵심 경로만 지금 고치고 나머지는 분리 C) 다른 접근 재검토
- 임시 로그와 단언은 제거한다.

### 6. 검증과 보고
- 원래 재현 절차로 고쳐졌는지 확인하고, 전체 테스트를 실행해서 출력을 첨부한다.
- 보고 형식:
```
DEBUG REPORT
────────────────────────────────
증상:        사용자가 본 것
근본 원인:    실제로 잘못된 것 (파일:줄)
수정:        바꾼 것 (파일:줄)
증거:        테스트 출력, 재현 결과
회귀 테스트:  파일:줄
관련:        INV/SEC/D-xx, TODOS, 같은 영역의 이전 버그
상태:        DONE | DONE_WITH_CONCERNS | BLOCKED
────────────────────────────────
```
- 근본 원인이 문서와 설계의 빈틈이라면(예: 명세에 없는 실패 모드) 해당 명세나 `ARCHITECTURE.md`에 반영할 것을 제안한다.

## 금지
- "일단 이렇게 고쳐 둘게요" — 임시 처방은 없다. 제대로 고치거나 넘긴다.
- "이걸로 고쳐질 거예요" — 실행해서 증명하기 전에는 말하지 않는다.
- 근거 없이 "원래 있던 문제" — main에서도 재현되는지 보여주지 못하면 "미확인"이라고 쓴다.
