# /gf-spec — 기능 명세 작성과 계획 잠금

입력: `$ARGUMENTS` (예: `06`, `06 publish`, 또는 기능 설명)

## 절대 규칙
- **코드를 작성하지 않는다.** 스캐폴딩도 금지. 산출물은 명세 파일 하나다.
- **질문은 한 번에 하나**, 항상 추천안을 붙인다: `추천: A — 이유`.
- 문서(`docs/DECISIONS.md`, `ARCHITECTURE.md`, `API.md`, `DB.md`, `SECURITY.md`)와 **다른 결정을 명세에 쓰지 않는다.** 다르게 가야 한다면 멈추고 "D-xx를 바꿔야 합니다"라고 보고한다(NEEDS_CONTEXT).
- 문서 내용을 복사하지 말고 **ID(D-xx, INV-xx, SEC-xx)로 인용**한다.

## 단계 (순서대로, 생략 금지)

### 1. 대상 확정
- `docs/PIPELINE.md` §4 로드맵에서 NN을 찾는다. 없으면 사용자에게 어디에 들어갈지 묻는다.
- 선행 명세의 상태를 확인한다(`docs/specs/`). 선행이 MERGED 이상이 아니면 알리고 진행 여부를 묻는다.
- 이미 `docs/specs/NN-*.md`가 있으면 새로 만들지 말고 그 파일을 갱신한다.

### 2. 근거 수집 (읽기)
- `docs/DECISIONS.md`에서 관련 D-xx, `ARCHITECTURE.md` §5에서 관련 INV-xx, `SECURITY.md`에서 관련 SEC-xx를 모은다.
- 관련 API와 DB 절을 읽는다.
- **현재 코드를 실제로 읽어서** "현재 상태" 칸을 채운다. 추측 금지, 파일 경로로 확인한 것만.
- PROPOSED 상태의 결정(D-27 이후)에 의존하면 명세에 그 사실을 표시한다.

### 3. 범위 도전
- 이미 있는 코드로 해결되는 부분은? 최소 변경은 무엇인가?
- 새 클래스와 파일 수를 세고, 더 적은 구성 요소로 가능한지 검토한다.
- 동시성, 인프라, 낯선 패턴이 있으면 **Spring/React 내장 기능부터 확인**한다(Search Before Building). 공식 문서 기준으로, 찾은 내용과 출처를 명세에 한 줄씩.
- 범위 밖으로 뺀 것은 "제외" 칸에 이유와 함께 쓰고, 나중에 할 것은 `TODOS.md`에 추가한다.

### 4. 설계와 실패 모드
- 흐름을 ASCII로 그린다. 상태가 바뀌는 작업은 **큐 안/밖을 구분**해서 표시한다(INV-01, INV-02).
- 새 경로마다 현실적인 실패를 하나 이상 적는다(네트워크 끊김, 동시 요청, 페이지 넘김 중 요청, AI 타임아웃, DB 실패, 더블클릭, 뒤로가기, 오래된 상태).
- 각 실패에 대해 처리 방식, 사용자에게 보이는 결과, 테스트를 적는다. **테스트도 처리도 없고 조용히 실패하면 critical gap**으로 표시한다. critical gap이 남아 있으면 승인을 요청하지 않는다.

### 5. 수용 기준과 테스트 계획
- 수용 기준은 Given/When/Then으로 **테스트 가능하게** 쓴다.
- 해당 SEC마다 "거부되는지" 확인하는 기준을 넣는다.
- 테스트 계획: 단위(순수 로직), 통합(MySQL Testcontainers, STOMP), QA 시나리오(다중 클라이언트, 브라우저 확인 항목).
- "회귀를 잡지 못하는 테스트"는 계획하지 않는다(자기 setup만 검사하는 테스트, 구현을 그대로 베낀 테스트).

### 6. 작성과 검토 요청
- `docs/specs/_TEMPLATE.md` 형식으로 `docs/specs/NN-<이름>.md`를 작성한다. 상태는 `DRAFT`.
- 결정이 필요한 항목은 하나씩 질문해서 확정한다.
- 끝나면 요약을 보고한다: 범위, 건드리는 INV/SEC, critical gap 수, 미해결 질문.
- 마지막 줄에 **"G1: 팀원이 명세를 검토하고 상태를 APPROVED로 바꿔야 구현을 시작할 수 있습니다."**라고 쓴다. 스스로 APPROVED로 바꾸지 않는다.

## 완료 상태
- `DONE` — 명세 작성 완료, critical gap 0
- `DONE_WITH_CONCERNS` — 작성했으나 PROPOSED 결정 의존이나 미해결 질문이 있음 (목록 제시)
- `NEEDS_CONTEXT` — 결정 변경이 필요하거나 답을 못 받음
- `BLOCKED` — 선행 명세 미완료 등
